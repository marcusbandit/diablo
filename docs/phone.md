# The phone app

The Diablo app for Android, in `phone/`. React Native through Expo (SDK 58, React Native 0.88,
the new architecture, Hermes), TypeScript, expo-router. It replaced the Kotlin, Compose and Rust
app in 0.6.0 (issue #69) so a change is a fast refresh instead of a native build. The package is
still `com.marcusrosado.diablo`, versionCode 9, so it installs over the Kotlin app.

## Goals

- One Diablo, many sections. "Diablo" is the whole of him. A section such as Workout or Home is
  a focus with its own conversation and panel, and he still knows everything else inside it.
- Sections are data, not code. The hub's list is the truth; the phone keeps a copy.
- Native rendering of what the agents send: Markdown, Diablo's own blocks, and whole HTML pages
  in a sandbox.
- It works with what is reachable. With no hub up, every section and its history still opens
  from the phone's own store, and new messages wait in an outbox.
- Every posture of a foldable: the phone screen, the open inner screen, and half folded.

## Layout of the code

```
phone/app/                 routes (expo-router): index, settings, onboarding, scan, +native-intent
phone/src/model.ts         the one state of the app, the sync loop, pairing, notifications
phone/src/store/           the SQLite store (expo-sqlite) behind a small Sql interface
phone/src/sync/outbox.ts   sending the outbox in order, and what each failure means
phone/src/md/              the Markdown reader (pure TypeScript) and its native renderer
phone/src/blocks/          the block renderer registry and the sandboxed HTML view
phone/src/screens/         Shell (the posture layout), chat, panel, sections, settings, onboarding
phone/src/posture.ts       where the panes go for a window and a hinge (pure, tested)
phone/modules/diablo-posture   Expo module (Kotlin): FoldingFeature and the hinge angle sensor
phone/modules/diablo-listener  Expo module (Kotlin): the background listener and notifications
phone/plugins/             config plugins: activity config changes, the signing key
phone/scripts/             emulator, build, run, shot, fold, create-avd, fake-hub
packages/hub               @diablo/hub, the hub client shared with the web app
```

`phone/android/` is generated by `expo prebuild` and never edited or committed. Everything native
lives in `app.config.ts`, the config plugins and the two local modules.

## The hub client

Every call goes through `@diablo/hub` (`packages/hub`): `Hub`, `sseParser`, `parsePairLink`,
`normalizePairCode` and the wire types. The phone passes `expo/fetch` as the fetch, because React
Native's own fetch cannot read a response as it streams, and the event stream needs that.

## Hubs

The app keeps an ordered list of hubs: any hub a pairing link named first, then the Pi
(`DIABLO_HUB_URL`, default `http://diablo-pi:8755`), then the standby (`DIABLO_STANDBY_URL`, no
default). Both are read at build time by `app.config.ts`, from the environment first and then
from `~/.config/diablo/local.env`, and land in `expo.extra.hubs`. Real values never live in the
repo; a build on a box without them still reaches any hub a pairing link names. Traffic is plain http over the
tailnet, so cleartext is allowed (expo-build-properties).

Each round of the sync loop pings `/v1/health` on each hub in order and uses the first that
answers, keeping how fast each one was for settings. The standby answers health only while the
Pi is down (docs/standby.md), so the phone moves to it and back on its own.

## Pairing

The phone never holds hub_token. It pairs: Diablo makes a one-time code (Telegram `/pair`, the
brain's pair_device tool, or Pair a device on the hub's web page), the phone sends it to
`POST /v1/pair` and gets a token of its own. The code reaches the phone three ways:

- typed, as `ABCD-EFGH`;
- scanned: Scan QR code opens Google's code scanner through expo-camera's `launchScanner`, which
  needs no camera permission; where Google Play services lack it, `/scan` uses the in-app camera
  after asking for the permission;
- tapped, as `diablo://pair?host=..&code=..`. The root layout reads the link and shows the
  pairing in a dialog over whatever is on screen. A code that names a hub this phone has not used
  asks before it pairs.

The token lives in expo-secure-store (the Android keystore), never in SQLite. Pairing again
revokes the phone's previous device. Unpair in settings revokes the device on the hub and forgets
the token; when the hub does not hear it, settings says to revoke it with `/devices`.

The APK is signed with the machine's own debug key (`~/.android/debug.keystore`, or
`$DIABLO_DEBUG_KEYSTORE`), the key the Kotlin app was built with, so 0.6.0 installs over 0.5.x.

## Offline and the store

`src/store/store.ts` keeps, in `diablo.db`:

- `sections`, as the hub last sent them;
- `messages`, by hub id, per section;
- `outbox`, his lines that have not reached the hub, in the order he wrote them;
- `panels`, each section's last panel;
- `kv`: the current section, each section's pull cursor and read mark, the device, onboarding.

A section always draws from the store first. A pull asks for `after=<cursor>`; the first pull of
a section takes the newest 200 messages, and scrolling to the top pages back with `before=`.

Sending writes the line to the outbox and then flushes it: one line at a time, oldest first,
across all sections, through `POST /v1/chat` with a `client_id`, so a retry never runs twice on
the hub. No answer, a 409 (the same line still running) or a 503 (the standby takes no turns)
leaves the line queued and stops the flush; a 401 or 403 marks the phone as no longer known; any
other refusal marks that one line failed, with Retry and Discard under it, and the next goes. A
user message that comes back from the hub with the line's `client_id` clears it from the outbox,
so it does not matter whether the reply or the event stream brings it first.

## Live updates

While the app is on screen it holds `/v1/events?ping=30` through `expo/fetch`:

- `turn` shows Thinking, then each `doing` step, in the chat header, under the section in the
  list, and as the last row of the conversation; `done` or `failed` clears it and pulls;
- `message` pulls that section;
- `sections` fetches the list again;
- `panel` refetches the current section's panel when it shows one of the modules, except right
  after a tap of its own;
- `question` patches the question block inside the stored reply.

The stream stops when the app leaves the screen; the background listener takes over.

## Rendering

Every reply is Markdown, read by `src/md/parse.ts` into a flat list of blocks and drawn with
React Native views:

| Content | How it is drawn |
|---|---|
| Headings, paragraphs, lists, task lists, quotes, rules | native Text and View |
| Bold, italic, code, strikethrough, links, autolinks, `<br>`, `<b>` and friends | nested Text spans |
| Code blocks | monospace, horizontal scroll, Copy |
| Tables | horizontal scroll, columns sized from their longest cell |
| Pictures | expo-image (GIF and animated WebP included) |
| HTML blocks, `html` and `svg` fences | the sandboxed HTML view |
| Diablo's blocks in `meta.objects` and panels | the registry in `src/blocks/Blocks.tsx` |

The registry draws `goal`, `stats`, `progress`, `bars`, `list`, `actions`, `notice`, `image`,
`code`, `diff`, `question`, `table`, `readout`, `html`, `lamps` and `scenes`. A new kind is one
component and one line; a kind the app does not know is skipped. Taps go through one context:
`say` (send a line or fill the composer), `act` (`POST /v1/act`, the fresh panel replaces the old
one, a failure shows its `detail`), `answer` (`POST /v1/questions/{id}/answer`), `open` (go to the
section that shows a module) and `file` (a stored file's URL with the `X-Diablo-Token` header,
which expo-image sends).

The HTML view is react-native-webview with JavaScript, DOM storage, file access and multiple
windows off, mixed content never, and a Content-Security-Policy injected first in the page that
allows only inline styles and `data:` pictures and fonts, so nothing loads from the network. The
page gets the app's colours as the CSS variables the desktop gives it (`--bg`, `--ink`, ...).

A section's panel sits above its chat: the `goal` blocks first, every `actions` block gathered
into one row of chips, then the cards. It folds to one line that carries its main number, and
scrolls inside itself up to about half the pane.

## Postures

`modules/diablo-posture` is an Expo module in Kotlin. It reads Jetpack WindowManager's
`FoldingFeature` for the app's window (state, orientation, separating, occlusion and bounds in
dp) and the hinge angle sensor (`Sensor.TYPE_HINGE_ANGLE`, 180 is flat), and sends both to
JavaScript on every change. React Native has no API for either. `expo-hinge` (SDK 58) reports the
angle and a status but not the bounds or the orientation, which the layout needs to keep the seam
clear.

`layoutFor` in `src/posture.ts` turns a window size and that snapshot into two rectangles, the
sections pane and the chat pane:

- **Phone** (under 600 dp wide): the chat fills the screen and the sections are a drawer behind
  the menu button.
- **Wide** (the open inner screen, or a phone on its side): the sections list beside the chat.
- **Book** (the hinge bent and running top to bottom): the sections on the left half, the chat
  on the right half, nothing on the seam.
- **Tabletop** (bent, running across): the conversation fills the top half; the sections list and
  the composer, the controls, share the bottom half. On a phone-width window the sections stay
  in the drawer and only the composer moves below the hinge.

Bent starts at about ten degrees from flat: under 170 degrees on the hinge sensor, and above 25,
which is a closed phone. The system's own half-opened state needs a much deeper bend. The main
activity declares the configuration changes a fold makes, so it never restarts on a fold.

There is one layout tree for every posture: the Shell always holds the same two panes and only
their rectangles change, with a LayoutAnimation glide on a change and none on the first frame.
The chat pane always holds the same three pieces (content, the hinge's gap, the composer); in
tabletop the gap gets the hinge's height and the composer moves right of the sections. Settings and onboarding keep to the right half in book
posture; onboarding shows the wordmark on the left half.

## Back

- A dialog (the pairing link, a confirm) closes first.
- On a phone, an open drawer closes.
- Any section other than Diablo returns to Diablo.
- Settings, the scanner and a replayed introduction go back where they came from; the
  introduction steps back one page, and from its first page leaves.
- Only the Diablo section with nothing open leaves the app.

Predictive back is on (`android.predictiveBackGestureEnabled`, which sets
`enableOnBackInvokedCallback`).

## Notifications

When the app is in the background, a new reply from Diablo in any section becomes an Android
notification. There is no Google push: the phone holds the hub's own event stream over the
tailnet, from a foreground service.

The approach is a small Expo module, `modules/diablo-listener`, in Kotlin, the same design as
the Kotlin app's listener. The alternatives were weighed:

- notifee runs a JavaScript task inside its foreground service. Its last release (9.1.8) is
  well over a year old, it does not come back after a reboot, and the stream would need the
  whole JavaScript runtime awake in the background.
- expo-notifications posts local notifications but has no foreground service, and its push path
  needs Google.

The module needs no JavaScript to run, so it also starts after a reboot and an app update.

- `ListenerService` is a foreground service of type `remoteMessaging`. It keeps
  `/v1/events?ping=240` open with `HttpURLConnection`: the hub sends a keepalive every four
  minutes, so the socket is silent between events and the radio can sleep. A read timeout of
  two keepalives and a half counts a silent socket as lost. Each event is handled under a 30
  second wake lock; reconnects back off from 10 seconds to five minutes and restart at once when
  the network comes back.
- On every connect it fetches the sections and catches up on each, so a reply that landed while
  the stream was down still notifies. Each section has a `seen` cursor in the module's own
  SharedPreferences. A cursor that does not exist yet only lets through replies newer than the
  moment notifications were turned on.
- Only `assistant` messages notify, never superseded ones, and never the section on screen while
  the app is in front (`setPresence`).
- Each section is its own channel (`section-<id>`), named after it and lit in its accent, and its
  replies stack into one notification (up to six lines) that opens the section through
  `diablo://section/<id>`. Markdown is flattened to plain lines by `Plain.kt`; tables, code and
  pictures become a short summary.
- The quiet "Listening for Diablo" notice is the one Android requires for a foreground service,
  in its own minimum-importance channel that can be switched off.
- The JavaScript side calls `configure` with the hubs, the sections, the switch and the token.
  The listener keeps its own copy of the token, sealed with an AES key that never leaves the
  Android keystore. It runs only while the switch is on, the phone is paired and Android allows
  notifications. `BootReceiver` starts it after a reboot or an update.

Onboarding asks once, after showing what a notification looks like with the real sections and
their latest replies; settings holds the same switch, Send a test and the channel settings.

## Onboarding

First launch shows four pages before the main screen: what Diablo is (the sections and a live
goal card), pairing (what it unlocks, what it costs, then the code), notifications (two previews,
then the switch) and ready. Each step can be skipped. A skipped pairing leaves "Not paired" in the
chat header and the sections list, which open settings. Settings has Show it again, which opens
the introduction with a close button.

## Building and checking

On the build box every Gradle build goes through `buildq`:

```
cd phone
buildq --local -- scripts/build.sh debug     # prebuild when needed, then assembleDebug, x86_64 only
buildq --local -- scripts/build.sh release   # its own bundle, arm64-v8a and x86_64, debug-key signed
scripts/emulator.sh                          # diablo_phone (Pixel 10 Pro Fold), headless; reuses a running one
bunx expo start                              # Metro, for the debug build
scripts/run.sh debug                         # install and launch (adb reverse for Metro)
scripts/fold.sh fold | unfold | half [deg] | state
scripts/shot.sh name                         # PNG from the active display into captures/
bunx tsc --noEmit                            # typecheck
bun test test                                # store, outbox, Markdown and layout tests
```

`build.sh` runs Gradle in a systemd scope capped at 7000 MB with swap forbidden. Reanimated,
worklets and gesture-handler are optional peers of expo-router that the app does not use; they
are left out of autolinking in `package.json`, which keeps their C++ out of the build.

### A fake hub

`scripts/fake-hub.sh start` runs the real `hub/` code on a throwaway data dir with invented
sections, messages, panels and a fake brain, and prints a pairing code and a
`diablo://pair?host=http%3A%2F%2F10.0.2.2%3A8755&code=...` link for the emulator.
`fake-hub.sh say [--in SECONDS] <section> "text"` posts a reply later, for the notification path;
`fake-hub.sh code` mints another code; `fake-hub.sh stop` ends it.

The hub list is baked into the APK at build time, so a debug build made on this box points at
the real hubs. For the fake hub, either build with
`DIABLO_HUB_URL=http://10.0.2.2:8755 DIABLO_STANDBY_URL=http://10.0.2.2:8799` (pass them through
`buildq --env`), or start Metro with `EXPO_PUBLIC_DIABLO_HUBS=http://10.0.2.2:8755,http://10.0.2.2:8799`,
which Metro writes into the JavaScript bundle and which wins over the baked-in list. Never build
a release for a person with that variable set.

### The emulator and the fold

`diablo_phone` is a Pixel 10 Pro Fold profile. Its system image has no display-feature config
for that device, so WindowManager reports no `FoldingFeature` and the app could not see the
hinge's position. The image does carry the Pixel 9 Pro Fold overlay, whose inner screen and
hinge are the same; `scripts/fold.sh` switches it on (`cmd overlay enable
com.android.internal.emulation.pixel_9_pro_fold`) before it moves the hinge. A real Fold reports
its feature without this.
